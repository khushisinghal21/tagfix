How each set was written

    Held-out 3: first-run misses

      All three failed safe: the customer got a person, not a wrong answer. One caveat applies to every set: I wrote both the messages and the rules. The real test is a few hundred of Park+'s own tickets.

      The problem

      • Nearly half of the FASTag help is about one transaction. Of the 43 FASTag articles in Park+'s help centre, 19 cover toll charges, recharges and blacklisting: charged twice, wrong amount, charged without crossing, recharge not credited, passbook missing.
      • Customers get templates, not answers. App Store reviews of Park+ describe "copy-paste" support replies, a failed FASTag payment that took 48–72 hours to sort out, and developer responses that send everyone to the same support email.
      • Refunds are slow and opaque. Users on forums like Team-BHP report wrong-deduction refunds taking 25–30 days through the bank, often after a first rejection.
      • A new category has arrived. NHAI had issued 77 lakh+ Annual Passes by July 2026, about a third of car toll transactions. "Charged even though I have the pass" isn't in the help centre yet.

      What TagFix changes

      • The first reply is about this customer's transactions, not a help article. Every amount and ID in it traces to the passbook.
      • When the data proves an error, the dispute goes out with evidence attached, so the bank has less reason to reject it.
      • When a charge is correct (a return-trip fare, a state expressway not covered by the pass, a toll posted days late), it explains why, which is where most "copy-paste" frustration comes from.
      • When it isn't sure, it hands off with the context so the customer doesn't repeat themselves.

      How I'd measure it

      • Main metric: share of FASTag tickets closed correctly without an agent.
      • Guardrail: wrong-action rate, meaning a wrong refund filed or a wrong "your charge is correct". Target zero in shadow mode before anything goes live. One wrong "this is correct" costs more trust than ten handoffs.
      • Reopen rate within 7 days. Time to first useful reply. Dispute acceptance rate by the bank, which tells you whether the evidence works. CSAT on resolved chats.

      How I'd roll it out

      1. Shadow mode. Run on last month's FASTag tickets offline and compare with what agents did. This replaces my 90 self-written messages with a real number.
      2. Agent assist. Show the draft reply and evidence in the agent console. Track how often agents send it unchanged.
      3. Auto-reply where no money moves. Explanations first: return trips, late postings, pass coverage, used-up passes.
      4. Auto-file disputes once the bank's acceptance rate for evidence-backed disputes is known.

      Risks

      • Telling someone a wrong charge is correct. It only explains when a deterministic check says so; anything else goes to a person.
      • Stale data. Late postings and pending reads change the picture. Checks use read time, not SMS time.
      • Rules change often (Feb 2025 blacklist timing, Nov 2025 UPI rate, Annual Pass, KYV changes). Every policy number lives in one file.
      • An LLM inventing numbers. It can only rephrase; a rewrite that changes any amount, time or ID is thrown away.

      What I'd need from Park+

      • A few hundred anonymised FASTag tickets with how they were closed, to replace my test sets.
      • Which fields the issuer banks actually return: read time vs posted time, plaza ID, vehicle class, decline codes.
      • Whether Park+ can see a tag's Annual Pass status, or only the ₹0 crossings.
      • Current dispute turnaround by bank, so replies quote Park+'s real numbers.

      1. Read the message

        Keyword rules for English, Hinglish and Hindi. Optionally an LLM, whose answer must be one of the known issues or it's ignored.

      2. Look at the account

        If the message is vague, or the customer's claim doesn't check out, but the passbook shows exactly one problem, answer that and say so. Non-FASTag topics (car wash, challan, parking) are never pulled in.

      3. Check the facts

        Plain code decides what's true: duplicates, tariff by vehicle class, return-trip fares, Annual Pass coverage and trips, read vs posted time, impossible travel between plazas, stuck recharges, blacklist reason.

      4. Act and reply

        Resolve, file a dispute with evidence, ask one question, or hand off. The reply is built from the checked facts, so every amount and ID traces to a transaction.

      Rules it applies

        What's real and what isn't

        • Plaza names, coordinates and operators are real, so distances and Annual Pass coverage are real. Tariffs, accounts and transactions are made up.
        • The LLM layer (reading messages and rewriting replies in the customer's language) is built and unit-tested with a mocked model. It hasn't been run against live traffic, and this page runs without it.
        • An LLM rewrite is thrown away if it drops or changes any amount, time, UPI reference or transaction ID.
        • Everything on this page runs in your browser. Nothing is sent anywhere.
